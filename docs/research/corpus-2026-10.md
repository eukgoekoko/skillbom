# License landscape of public agent skills — corpus study, October 2026

We scanned 1,211 public GitHub repositories that contain agent skills: 62,704 distinct skills and 3,578 plugins. The question was simple: when a company installs a public skill, can it tell what license that skill is under?

The numbers below come from `skillbom` 0.1 with the detector fixes described under [Accuracy](#accuracy), re-run on 2026-10-23. On a held-out sample of 100 skills, the scanner matched hand labels on every unambiguous case.

## Headline findings

1. **Licenses live at the repo root; skills travel alone.** 92.5% of the repos have a root LICENSE, but only 22.5% attach a license to *every* skill itself, in the SKILL.md frontmatter or a license file in the skill's folder. **81.3% of all skills are licensed only through the repository or plugin they sit in**: 57.0% through a parent plugin manifest and 24.3% through a LICENSE file higher up. Another 2.5% have no license anywhere. Skills are installed by copying a single folder into `~/.claude/skills/`, and that copy carries no license.
2. **The official marketplace licenses whole plugins, not skills.** Its plugins usually declare a license in `plugin.json`, so only 4.1% of its 195 repos with skills contain a skill with no license at all, against 5.2% across the corpus. But it is the *least* likely to license skills individually: just 15.9% of its repos do this for every skill, against 22.5% overall. A skill copied out of a marketplace plugin loses its license.
3. **Restrictive licenses are rare but real.** Repos with at least one skill under each type of license:

   | license type | share of repos |
   |---|---|
   | copyleft (GPL, AGPL, LGPL, MPL, CC-BY-SA) | 4.1% |
   | proprietary | 2.2% |
   | non-commercial (CC-BY-NC*, PolyForm Noncommercial, BUSL) | 1.8% |
   | source-available with service restrictions (Elastic, FSL, Commons Clause) | 0.8% |
   | custom terms that need a human to read them | 0.8% (2.1% in the official marketplace) |

   At skill level: 681 skills don't permit commercial use, and 1,226 more are under organization-specific `LicenseRef-` terms (mostly declared in plugin manifests) or licenses we don't map yet.
4. **Proprietary skills are being redistributed.** 12 repos outside Anthropic ship copies of Anthropic's document skills (docx, pdf, pptx, xlsx), 47 copies in total (some repos ship the same skill in more than one folder). Each copy still carries its "© Anthropic, PBC. All rights reserved" LICENSE.txt, which ties use to the user's agreement with Anthropic. Some of these repos are popular "awesome" collections, and at least one has no license of its own. Whether this is permitted is a legal question we don't answer. A company that installs from these collections inherits that question without knowing it.
5. **Nobody declares licenses in machine-readable form yet.** 15.7% of skills use the SKILL.md `license:` key (27.6% in the official marketplace), and about 2% of those values are free text rather than SPDX ("Proprietary. LICENSE.txt has complete terms", "SEE LICENSE IN LICENSE", "BSD-3-Clause license"). No skill uses a dedicated license file, as expected, since the format is ours and new.

Taken together: for more than four out of five public skills, an installed copy says nothing about its license. That is the gap a Skill BOM and a skill-level license file are meant to close.

## Accuracy

We measured detection against hand labels in two rounds. In each round, one random skill was taken from each of N randomly chosen repos. That weighting matches the per-repo headline numbers and keeps one huge repo from dominating.

1. **Labeling.** For each skill, a script assembled the raw evidence: license lines in its SKILL.md, license files and plugin/package manifests in its folder and every parent folder up to the repo root. The labeler saw this evidence but not the scanner's verdict.
2. **Truth.** The true license is the skill's own declaration if it has one, otherwise the *nearest* parent declaration. A plugin manifest outranks the repo root. GNU licenses are compared without the `-only`/`-or-later` suffix, which a license text alone doesn't settle.
3. **Ambiguous cases** are counted but marked separately. Example: a plugin declaring MIT inside an AGPL-3.0 repository.

| | training set (blind) | held-out set |
|---|---|---|
| Sample | 200 skills from 200 repos | 100 skills from 100 other repos |
| Scanner version | before the fixes below | after the fixes |
| Exact license | 94.5% (95% CI 90.4–96.9) | **98.0%** (93.0–99.4) |
| Exact license, unambiguous cases | 96.4% | **100%** (96 of 96; CI 96.2–100) |
| License category | 97.0% | **100%** (96.3–100) |
| "Has its own license" agreement | 99.5% | **100%** |
| "No license found": precision / recall | 81.8% / 100% | **100% / 100%** |

The training round found five detector problems, fixed before the held-out round:
- **GPL read as AGPL.** The GPL-3.0 text mentions the "GNU Affero General Public License" in section 13. GNU licenses are now identified by their heading.
- **Every GNU text read as "-or-later".** The license's own "How to Apply" appendix contains "any later version". Now only a notice before the appendix counts.
- **Parent plugin manifests were ignored for skills,** which caused both "no license" false alarms. Now the nearest parent declaration counts, whether a manifest or a LICENSE file.
- **An MIT file mentioning Apache-licensed third-party code was read as Apache.** A recognized title line now wins over phrases further down.
- **`## License` sections in the SKILL.md body were ignored.** They now count as the skill's own declaration.

The remaining held-out disagreements are both repos that license documentation (CC-BY-4.0) and code (MIT) separately. The scanner reports "CC-BY-4.0 OR MIT", and the label says CC-BY-4.0 because a SKILL.md is closer to documentation.

**Caveat:** the labels were made by the same team (with Claude) that wrote the scanner. They are not an independent audit. The published tables list every sampled skill's repository and path with both verdicts, so anyone can re-check them: [training set](accuracy-train-2026-10.csv), [held-out set](accuracy-holdout-2026-10.csv). `scripts/corpus/sample.py` and `scripts/corpus/accuracy.py` reproduce the rounds.

## Corpus and method

| | |
|---|---|
| Candidate repos | 1,511: the external sources of the official Claude Code marketplace (227) plus GitHub repository search for skill/plugin topics, sorted by stars (no forks, no archived repos) |
| Fetched | 1,495 (16 failed: timeouts, unreachable or deleted repos) |
| Containing skills | 1,211; median 5 skills per repo |
| Distinct skills / plugins | 62,704 / 3,578 (deduplicated by content hash; 157 skills appear verbatim in several repos) |

Scripts are in `scripts/corpus/`: `collect.py` builds the list, `fetch.py` fetches only the skill-relevant files, and `analyze.py` runs the scanner and aggregates. Raw per-repo BOMs land in `.corpus/`, which is not committed.

- Each repo is scanned as a whole with `--root`. A skill inherits the nearest parent declaration up to the repo root, which matches how a careful human would read the repo.
- Detection is heuristic: SPDX expressions in manifests and frontmatter, free-text license names, and the titles and key phrases of license texts (see the [scanner reference](../scanner.md#license-detection)). A license text that matches no known license counts as *custom*, not *none*.
- **Per-repo numbers are the headline.** Per-skill numbers are dominated by a few very large repos; one repo alone contributes about 23,000 skills under "Apache-2.0 OR MIT".

### Limitations

- **Sample:** this is a topic-and-marketplace sample, not a census. GitHub code search for `SKILL.md`, which needs a token, would reach repos without topics. The sample leans toward popular repos.
- **Snapshot:** one commit per repo (default branch HEAD), not the commit the marketplace pins.
- **Evidence scope:** only license files, manifests and SKILL.md were considered. License statements in READMEs or source-file headers were not.
- **Content hashes:** 198 repos were fully cloned and the rest fetched with a filter (files over 1 MB and non-skill files skipped), so copy detection across those two groups undercounts.
- **Legal status:** "non-commercial", "proprietary" and "custom" are classifications of the license text, not legal conclusions.

## Other detector improvements from this study

Fixes made while running the corpus, before the accuracy rounds:

- **Source-available licenses** are now recognized, both as texts and as table entries: PolyForm (Noncommercial, Small Business, Shield, Internal Use), BUSL-1.1, Elastic-2.0, SSPL-1.0, FSL-1.1 and Commons Clause (reported together with its base license). Before this, PolyForm Noncommercial went unrecognized.
- **Free-text names** in `license:` fields are now parsed ("GPLv3 license", "MIT + Commons Clause", Creative Commons URLs, npm `UNLICENSED`).
- **Pointer texts and translated licenses** are matched by their title line ("MIT License – see repository root LICENSE").
- **Unknown license texts** are reported as `LicenseRef-custom` with a `license-review` finding, instead of as "no license".
- **Own evidence beats inherited evidence** (found earlier on a real install). The study confirms it matters: many repos have a permissive root LICENSE but individual proprietary or non-commercial skills.
